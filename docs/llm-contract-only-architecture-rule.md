# Critical Architecture Rule — LLM Generates Contracts Only

> Governing design principle for the Transformation Spec → AI Rules feature.
> Companion to [`transformation-spec-architecture.md`](./transformation-spec-architecture.md).
> This rule is **non-negotiable** and already matches the invariant the
> `recon_engine` package is built on (`recon_engine/__init__.py`:
> *"LLM output = Data, Engine output = Execution"*).

## Non-Negotiable Design Principle

The Groq LLM must **NEVER**:

- Modify source data
- Modify target data
- Execute transformations
- Generate executable Python
- Generate SQL
- Generate pandas code
- Rewrite connector outputs
- Update SAP data
- Persist transformed datasets

The LLM's sole responsibility is:

**Convert transformation specifications into a structured Transformation Contract JSON.**

Nothing else.

---

## Correct Processing Lifecycle

### Stage 1 — Dataset Acquisition

Source/target datasets are fetched normally (SAP S/4, SAP IBP, Excel, CSV) and
become:

```text
Raw_Source
Raw_Target
```

Both datasets must remain **immutable** — never modified, never overwritten, never
persisted back to the connectors.

### Stage 2 — Contract Compilation (LLM)

Inputs: Mapping Sheet, User Rules, Comparison Type, Source Schema, Target Schema.

Groq generates a **contract only** (no execution here):

```json
{
  "business_key": [...],
  "compare_fields": [...],
  "operations": [...]
}
```

### Stage 3 — Validation

- **Gate 1 — structural:** schema validity, allowed operations, valid fields, valid
  parameters.
- **Gate 2 — sample replay:** run against 50–100 sample records; verify operations
  execute, fields exist, outputs are valid.

### Stage 4 — Human Approval

Approved Draft Contract becomes `TransformationContract v1`. Store `contract_id`,
`version`, approval metadata. **No data transformation occurs yet.**

---

## Runtime Execution

Input: `Raw_Source` + `Raw_Target` + Approved Contract.

The **deterministic engine** executes the contract's operations, e.g.:

```json
{ "op": "trim_string", "field": "MATNR" }
```

producing a temporary in-memory `Shadow_Source`:

```text
Raw_Source     MATNR = 00012345
Shadow_Source  MATNR = 12345
```

**Raw_Source and Raw_Target remain unchanged.** Only `Shadow_Source` is transformed.
Never write transformed values back to SAP S/4, SAP IBP, Excel files, CSV files, or
stored source datasets.

---

## Reconciliation

Compare `Shadow_Source` **vs** `Raw_Target` using business keys, compare fields,
tolerances, and matching rules. Perform a `FULL OUTER JOIN`, then classify each
record using the existing reconciliation engine.

---

## Required Execution Flow

```text
Mapping Sheet + Rules + Schemas
      ↓
Groq LLM
      ↓
Draft Contract
      ↓
Validation (Gate 1 + Gate 2)
      ↓
Approval
      ↓
Transformation Contract
================================
Raw_Source + Raw_Target + Approved Contract
      ↓
Deterministic Engine
      ↓
Shadow_Source
      ↓
Reconciliation Engine
      ↓
Results
```

---

## Explicit Prohibitions

Do **NOT**:

- ❌ Modify connector outputs
- ❌ Rewrite source datasets
- ❌ Rewrite target datasets
- ❌ Persist transformed records
- ❌ Execute AI-generated code
- ❌ Execute SQL generated by AI
- ❌ Allow the LLM to access runtime data
- ❌ Allow the LLM during reconciliation execution

The LLM participates **only** during contract compilation. All runtime execution
must be deterministic and implemented in the existing `recon_engine`.

---

## Alignment with the current implementation

This principle is **already enforced** by the existing code. Reference points:

| Rule | Enforced by |
|---|---|
| LLM emits JSON contract only, never code | `recon_engine/compiler/groq_compiler.py` system preamble ("JSON only… never emit SQL/Python/pandas"); `response_format={"type":"json_object"}` |
| Contract carries no code/expressions | `recon_engine/models/contract.py` — `ContractOperation` has `model_config = extra="forbid"`; comment: "no field for code, expressions, or scripts" |
| Only allow-listed operations may run | `recon_engine/operations/registry.py` — fixed allow-list; `get_operation()` raises `KeyError` for anything not registered |
| Gate 1 structural / Gate 2 replay | `recon_engine/validation/gate1_structural.py`, `gate2_replay.py` |
| Versioned approval | `recon_engine/models/contract.py` `TransformationContract` (`contract_id`, `contract_version≥1`, `approved_by`, `is_executable()` = APPROVED only) |
| Raw immutability | `recon_engine/storage/snapshot_store.py` — append-only, exposes no update/delete; `executor.build_shadow_source` copies, never mutates Raw_Source |
| Shadow_Source derivation | `recon_engine/engine/executor.py` (`build_shadow_source`, applies ops in order) |
| Full-outer-join + classification | `recon_engine/engine/reconciler.py` |
| No LLM at runtime | `recon_engine/engine/__init__.py`, `reconciler.py` ("no LLM at runtime"); Groq used only in `service.compile_draft` |

### Two gaps to close during implementation

These items appear in the rule's examples but are **not** present in the current
codebase and must be handled explicitly:

1. **`remove_leading_zeros` is not an allowed operation yet.** The registry currently
   allows exactly 11 ops: `identity_cast_string`, `trim_string`, `numeric_cast`,
   `date_parse`, `rename_field`, `reject_null`, `exclude_value`, `group_by`,
   `sum_aggregate`, `exact_match`, `tolerance_match`. To let the LLM emit
   `remove_leading_zeros` (e.g. for SAP `MATNR`), a developer must implement it in
   `recon_engine/operations/ops.py` and register an `OperationSpec` in
   `recon_engine/operations/registry.py`. This is the intended extension path — the
   allow-list is deliberately the boundary that stops the LLM inventing operations.
   Until added, Gate 1 will (correctly) reject any contract referencing it.
2. **"Tolerance Match" is not a separate result classification.** The engine's
   `RecordClass` (`recon_engine/models/results.py`) is `MATCH | MISMATCH |
   MISSING_IN_SOURCE | MISSING_IN_TARGET | EXCEPTION`. Tolerance is a compare-field
   `match_type` (`tolerance_match`) that resolves to a `MATCH`, not a sixth bucket.
   UI/reporting should treat within-tolerance records as matches (optionally
   annotated), not as a distinct class.
